# AMP — 제품·기능 상세 명세서 (PROJECT.md)

> **Amplify Local Stages. 작은 무대의 울림을 세계로.**  
> 2026 명지대학교 해커톤 · AI × K-콘텐츠: Local to Global · 5조  
> 버전 **v1.1** · 2026-11-06 · 상태: **개발 전 MVP 명세**

## 1. 제품 목적 및 문제 정의

**AMP**는 신촌·홍대 인디 공연을 **발견(Discover) → 선택(Decide) → 방문 준비(Visit)**할 수 있게 돕는 AI 로컬 공연 큐레이터다. 공연 제공자는 **포스터 이미지 업로드 → 정보 추출 → 기존 공연장 매칭 → 검수 → 등록(Amplify)** 흐름을 이용한다.

### 해결하려는 문제

- 기존 공연 정보 플랫폼이 있더라도, 관객은 예산·날짜·분위기·관람 방식에 맞는 후보를 **직접 여러 개 비교**해야 한다.
- 입장 시작 시각·건물 층수·비지정석/선착순·드링크 규정 등 행동에 필요한 정보가 **긴 개별 공연 공지 속에 흩어져** 있을 수 있다.
- 외국인은 다국어 메뉴가 있어도 **공연별 한국어 안내문**을 이해하기 어려울 수 있다.
- 포스터만 가진 공연 제공자는 등록 필드를 다시 입력하고 기존 공연장을 찾아 연결하는 수작업이 남을 수 있다.

**주장 범위:** 인디스트릿은 공연/장소/아티스트 정보와 **텍스트 기반 날짜·가격·아티스트 자동 추출**을 제공하는 것으로 직접 확인했다. 장소는 기존 DB에서 직접 선택하며 등록 폼에서는 장소 선택이 필수가 아니다. 포스터 이미지 자동 추출·상황별 AI 추천은 현재 확인한 범위에서 **미확인**이며 '절대 없음'으로 표현하지 않는다. AMP의 실제 개선 효과는 비교 실험 전까지 가설이다.

### 목표 사용자 및 경험

| 사용자 | 현재 해야 하는 일 | AMP가 줄이려는 행동 |
|---|---|---|
| 공연 초심자 | 공연별로 날짜·가격·관람 방식 비교 | 자연어 입력 후 근거 있는 3개 이내 후보 확인 |
| 해외 방문객 | 긴 한국어 공지/현장 규칙 해석 | 방문 준비 카드의 검수된 한·영 핵심 안내 |
| 공연 제공자 | 포스터 정보 재입력, 장소 목록 수동 검색 | 이미지 기반 자동 입력 + 자동 DB 매칭 시도 + 사람 검수 |

### 성공 기준

1. **P0:** 실제 DB에 존재하고 하드 조건을 만족하는 공연만 **최대 3개** 추천한다.
2. 추천 이유는 **DB에 있는 사실**만 사용하며 가격 종류(예매/현장/일반)를 구분한다.
3. 공연 상세에서 **입장 시각과 공연 시작 시각**, 가격·좌석 방식·공연장 위치 등을 이해하기 쉬운 카드로 제공한다.
4. 핵심 방문 안내의 **KO/EN 전환**이 동작하고 미번역값은 미확인으로 표시한다.
5. **P1/최종 시연 목표:** 포스터 → AI 추출 → 장소 자동 매칭/수동 선택 → 검수 → 등록 → 목록/조건부 추천 반영이 이어진다.
6. 비교 우위는 실제 측정한 동작 횟수·수정 필드 수 같은 근거로만 주장한다.

## 2. MVP 범위 및 우선순위

### P0 — 관객 핵심 흐름 (먼저 안정화)

- 시드 데이터(공연 최소 20건, 공연장 최소 4곳) 및 출처/DEMO 라벨.
- 자연어 추천, 날짜/지역/가격 **하드 필터**, 분위기/혼자 방문/좌석 **소프트 선호**.
- **좌석 필수 조건**(`seating_requirement`)은 명시된 행사별 `seating_type`이 일치할 때만 충족.
- 추천 최대 3개, **가격 출처를 나타내는 가격 카드**, 사실 기반 한 줄 추천 이유.
- 공연별 방문 준비 카드(입장 시작, 공연 시작, 예매/현장가, 관람·좌석 배정, 공연별 규칙).
- 공연장 기본 가이드(주소, 층수, 입구 사진이 있을 때만 표시) 및 KO/EN 전환.
- 로딩/결과 없음/정보 미확인/네트워크 실패 상태.

### P1 — 공급자 등록 흐름 (최종 데모 목표)

- 포스터 JPG/PNG/WebP(최대 5MB) 업로드.
- Vision LLM 추출: 제목, 일시, 장소명, 단일·예매·현장가, 라인업 및 명시된 장르.
- 기존 `venues` DB에 유일 정확 일치 시 매칭, 미일치/모호함 시 직접 선택.
- 사용자 수정·검수 후 `POST /api/events` 등록(기존 `venue_id` **필수**).
- 등록한 공연이 `GET /api/events`에 나타나고 추천 조건에 부합할 때 검색·추천에도 표시.

> **P1은 버리는 기능이 아니라 개발 순서를 P0 다음으로 둔 기능**이다. P1이 지연돼도 P0 검색→상세→방문 준비 데모는 독립 동작해야 한다.

### 제외(Out of Scope)

- 회원가입/완제품 인증, 신규 공연장 자동 생성, 아티스트·공연장 CRUD/프로필 편집.
- 예매/결제, 북마크, 커뮤니티, 밴드·세션 매칭, 관광 코스, 대량 실시간 SNS 크롤링.
- 미검수 긴 한국어 안내문의 자동 요약·번역·정책 추론, 벡터 DB/RAG/모델 학습.
- 좌석 실시간 재고, 실제 티켓 구매 가능 여부·공연 안전 보장.

## 3. 화면별 기능 상세

### S01. 홈·자연어 추천 (`/`)

**UI:** AMP 브랜딩, 500자 이내 검색창, 빠른 필터(날짜/지역/가격/분위기/혼자 방문/좌석 선호·필수), 검색 버튼, 로딩, 추천 카드 0~3개, 안내/오류/재시도.

**정상 동선**

1. 사용자가 문장을 입력하거나 필터 칩을 설정한다.
2. FE는 `POST /api/recommend` 호출. 서버는 LLM 의도를 추출하고 UI 필터로 덮어쓴다.
3. 서버는 발표 시점 기준 KST를 적용해 행사 상태·날짜·지역·가격·필수 좌석을 먼저 필터링한다.
4. 분위기·혼자 관람·좌석 선호로 점수를 계산해 최대 3개 반환한다.
5. FE는 적용된 조건, 공연 카드, 추천 이유, 가격 종류, `DEMO` 여부를 표시한다.

**카드 필수 항목:** 제목, 공연 시각(KST), 장소명/지역, 대표 가격+`price_basis`, 확인된 분위기 태그, 추천 이유, 공연 상세 링크, `DEMO`/`VERIFIED`.

**예시:** `11월 7일 홍대에서 혼자 갈 만한 2만 원 이하 공연. 좌석이면 좋겠어`는 좌석 **선호**; `스탠딩은 절대 안 돼`는 좌석 **필수**로 처리한다.

**완료 조건**
- [ ] `2만 원 이하`는 `max_price_krw=20000`, 미확인 가격은 제외, 확인된 무료는 0원으로 취급.
- [ ] 예매가 20,000원·현장 25,000원이면 예매 가격 기준으로 포함하되, 구매 가능을 보장하지 않음.
- [ ] 좌석 필수 조건에서 `seating_type=null|standing|mixed` 공연은 추천하지 않음.
- [ ] 좌석 선호는 다른 하드 조건을 만족한 후보 중 점수 가산에만 사용.
- [ ] AI가 DB에 없는 공연·가격·인기·안전을 만들어 추천하지 않음.
- [ ] 0건이면 `items=[]`와 안내, AI 장애 시 수동 칩 검색 또는 오류.
- [ ] 결과 최대 3개, 추천 시각은 KST로 변환.

### S02. 공연 상세·방문 준비 카드 (`/events/:id` 또는 모달)

**데이터:** `GET /api/events/{id}` + `GET /api/venues/{event.venue_id}`. 공지 데이터는 검수된 DB에서만 제공한다.

**첫 화면 방문 준비 항목 순서**

1. **입장 시작 시각(`doors_open_at`)**과 **공연 시작 시각(`starts_at`)**을 명확히 구분.
2. 예매가(`advance_price_krw`), 현장가(`door_price_krw`), 대표 가격, 예매 링크가 있으면 표시. 가격 미확인은 `확인 필요`.
3. 스탠딩/좌석/혼합(`seating_type`)과 지정석/비지정석(`seat_assignment`)을 따로 표시.
4. 공연별 입장 유의사항(`admission_notes_ko/en`)과 드링크 정책.
5. 공연장 이름·주소·건물 층수·입구 사진(있을 때)·입구 동선(`entrance_hint_ko/en`).
6. 데이터 출처, 검증일, `DEMO` 표시.

**정책 우선순위:** 행사 `seating_type`, `drink_policy`가 있으면 행사 정보 적용. 없을 때 장소 기본값은 **'공연장 기본 정보(행사별 확인 필요)'** 라벨로 보여준다. 공연별 안내와 장소 입구 안내는 서로 다른 항목이므로 둘 다 보여줄 수 있다.

**KO/EN 전환:** `description_*`, `admission_notes_*`, `entrance_hint_*`의 검수본만 전환한다. 영어 데이터가 없으면 한국어 원문+`English guidance not confirmed`를 표시한다. 원본에 없는 규칙을 자동 작성하지 않는다.

**완료 조건**
- [ ] `doors_open_at=null`이면 공연 시작시간을 복사하지 않고 미확인으로 표시.
- [ ] 입구 사진/층수/정책이 없으면 임의 이미지·층수·규정 생성 금지.
- [ ] 공연별 규정/기본 공연장 안내를 명확히 구분.
- [ ] 영어 토글이 주요 입장 안내에서 동작하고, 미검수 영문은 표시하지 않음.
- [ ] 예매 링크가 없거나 구매 가능이 검증되지 않았으면 구매 가능하다고 단언하지 않음.
- [ ] 모바일에서도 방문 준비 정보가 읽을 수 있게 정렬.

### S03. 공연 제공자 등록 (`/admin/register`) — P1

**UI:** 업로드, AI 분석 진행/실패, 추출 결과 수정 폼, 공연장 자동 매칭 결과, `GET /api/venues` 수동 선택, 경고, 검수 체크, 저장 버튼.

**흐름**

1. JPG/PNG/WebP 포스터를 업로드(5MB 이하).
2. `POST /api/posters/parse`가 `extracted`와 `venue_match`를 반환.
3. `matched`면 장소를 미리 선택해 제안하고 **사용자가 확인/수정할 수 있게** 한다.
4. `ambiguous`, `not_found`, `no_name`이면 `GET /api/venues`에서 **기존 장소를 직접 선택**한다. 신규 장소 생성은 없다.
5. 공연명·시각·가격 종류/금액·라인업 및 필요한 필드를 사용자 검수/수정.
6. `review_confirmed=true`와 유효한 기존 `venue_id`로 `POST /api/events` 요청.
7. 저장 성공 시 상세 또는 등록 완료 화면. 조건에 맞는 새 공연은 이후 추천에도 자연스럽게 포함.

**필드 설명:** 단일 가격만 있으면 `price_krw`/`price_basis=general`; 예매·현장가가 있으면 대표 가격은 서버가 최저 명시 금액으로 정한다. `price_basis`는 요청에서 받지 않는다. 포스터에 안 보이는 입장 시작/좌석/드링크/분위기는 자동 확정하지 않는다.

**완료 조건**
- [ ] 검수 체크 없이 자동 게시 불가.
- [ ] 유효한 DB 장소 없이 게시 불가. 불일치시 오류 및 선택 UI.
- [ ] 자동 매칭 확신 없는 경우 저장 전에 수동 선택 필요.
- [ ] AI 실패 시 수동 등록 가능, 중복 저장 방지/재시도 처리.
- [ ] 검수한 정보만 DB에 저장, 목록 조회/추천 조건 반영.
- [ ] 공개 환경에서는 인증 적용 전 관리자 등록 API 비노출.

## 4. 추천·가격·가이드 정책 요약

| 요구/데이터 | 서버 정책 | 화면 표현 |
|---|---|---|
| 특정 날짜/지역 | 하드 필터 | `applied_filters` 표시 |
| 예산 상한 | `price_krw<=상한`(NULL 제외) | `price_basis`로 예매/현장/일반 구분 |
| 좌석 필수 | 이벤트 `seating_type` 정확 일치만 | 미확인은 조건 충족으로 표시하지 않음 |
| 좌석 선호 | 하드 필터 후 +20점 | 확인된 경우만 추천 이유에 사용 |
| 분위기 선호 | 태그 1개당 +40점 | 검수된 태그만 근거 |
| 혼자 방문 선호 | 확인된 `solo_friendly=true` +20점 | 안전·만족을 보장하지 않음 |
| 공연별 정책 | 이벤트 값 우선 | 장소 기본값은 행사별 확인 필요 라벨 |
| 영어 안내 | 검수본만 사용 | 미확인은 한국어 + 미확인 표시 |
| 공연장 이름 미매칭 | 유효 ID 없이 등록 불가 | 기존 공연장 검색/수동 선택 |

### 시간 정책

- DB 저장 UTC, 프론트 표시는 KST. `today/tomorrow`는 서버의 `Asia/Seoul` 기준.
- 등록 시 `doors_open_at_local`은 명시됐을 때만 입력. 입장 시작이 공연 시작보다 늦거나 종료가 시작보다 빠르면 검수/수정 요구.

## 5. 데이터/법적·윤리적 제약

- 목표: 실제 검증된 정보 또는 명시적 `DEMO` 데이터. 총 공연 최소 20건 / 기존 공연장 최소 4곳.
- 데이터 수집·이미지 사용은 출처 정책과 저작권 확인 후 진행. 기존 서비스 정보·포스터의 무단 일괄 수집/재배포 금지.
- 예매 가능/실제 현장 정책/안전 등은 최신 확인이 없으면 추정하지 않는다.
- 지식 추정으로 잘못된 동선·입구·좌석을 만들지 않는다. 방문 전 공식 출처 재확인 안내.
- 사진 확보가 어려우면 `entrance_image_url=null`을 사용하고 서비스는 계속 동작한다.
- 정식 공개 배포에는 관리자 인증·스토리지 영속성·AI 요청 비용 통제 필요.

## 6. 비기능 요구사항

- 프런트·백엔드는 정의된 API JSON 계약을 먼저 공유하고, 더미 응답으로 병렬 개발 가능해야 한다.
- 주요 공개 GET API는 로컬에서 빠르게 동작하도록 설계하되 측정 전 성능을 약속하지 않는다.
- 검색 오류에도 입력값과 필터를 보존하고 재시도/수동 필터로 복구한다.
- 등록에는 이미지 타입·용량·임시 ID 검증, 백엔드 키 비공개, CORS 제한 적용.
- `DEMO`, 미확인 상태, 텍스트 언어를 시각적으로 구분하고 키보드 접근성을 확보한다.
- 공개 배포라면 로컬 SQLite/업로드 폴더에만 의존하지 않는다.

## 7. 90초 시연 및 비교 검증

| 구간 | 시연 | 주장 가능한 효과 |
|---|---|---|
| 0~10초 | 기존 플랫폼 존재 인정, 선택·방문 준비 문제 정의 | 범위를 좁힌 문제 정의 |
| 10~30초 | `11월 7일 홍대, 2만 원 이하, 좌석 선호` 자연어 추천 | 조건 추출과 추천 근거 |
| 30~45초 | 공연 상세 방문 준비 카드·KO/EN 전환 | 안내 정보 재구성 |
| 45~65초 | 권리 확인된 포스터 업로드·이미지 추출·DB 장소 매칭 | 등록 수작업 감소 가능성 |
| 65~80초 | 관리자 검수 → 등록 → 목록/조건부 검색 반영 | 실제 데이터 연결 |
| 80~90초 | Discover → Decide → Visit + Amplify | 전체 흐름 |

**필수 시연 데이터 규칙:** 등록할 새 공연이 기존 검색 조건에 맞는 경우에만 추천에 나타난다. 추천 순위를 강제로 조작하지 않는다. 데모를 위한 가상 데이터는 `DEMO`로 명확히 표시한다. `오늘`은 시연 당일을 기준으로 재생성하거나 고정 테스트 시계를 쓴다.

### 간단 비교 검증(개발 전/완료 후)

1. **관객 작업:** 동일한 공연을 기준으로 검색·가격 확인·입장 방식 확인·영문 안내 확인까지 실제 조작 횟수와 소요 단계를 기록.
2. **공급자 작업:** 동일한 포스터(실제 허가/가상 샘플)로 직접 입력 필드 수·수정 필드 수·등록 직전까지의 단계 비교.
3. 다른 서비스에 가상 공연을 공개 등록하지 않는다.
4. 결과를 재지 않고 '타사에는 없다/항상 더 빠르다'고 발표하지 않는다.
